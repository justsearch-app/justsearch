# Lane F stage D1 — reconfigure, generations, readiness: implementation checklist

Written from the three inputs 17.6 requires: the stage's row in `design.md` 17.3, `verified-facts.md`,
and a fresh, code-verified read at `be47faa40` (the stage B head; the facts were gathered
2026-09-09 by a read-only pass and every `file:line` below is at that commit). `design.md` is cited
by **section**; code by `file:line`. **C1 and C2 land before D1 and will move these lines**; 17.6's
stage-start re-grounding applies, and the rows of §1 that assume C1/C2 outputs are marked.

Stage D1 in one line (17.3 row D1): **the recomposable registry with applied and attempted
versions, beside-or-in-place composition, `generation-bound` and `restart required` in the config
register (7.4); `core.restart-worker` retired and its consumers re-pointed at reconfigure; the
generation cutover as a live in-process activation with the journal and replay, the failed-unit
default flipped, encoder A recomposed on refusal, lexical-only ingestion with deferred enrichment
in the in-place mode, the applied config version computed from the active generation's metadata
(7.4); the candidate footprint declared per model and free device memory read in-process;
readiness as a component vector with re-cut codes and `readinessNotice.ts`, the second
representation made a projection, start deadlines, local recovery and bounded escalation (7.6).**

## 3. Checklist items

Ordering: the registry and versions first (D1-1 to D1-4), since every later item writes into
them; then the footprint and mode (D1-5, D1-6); the generation transition (D1-7 to D1-10); the
restart-required path and the retirement (D1-11); readiness (D1-12 to D1-15); the harness (D1-16);
the sweep (D1-17). The branch is green after every item; §9 names the only reds.

### D1-1 — the recomposable registry, in `core`, bound by the root

Design 7.4 (first paragraph) and 3.2's ring rule. An interface in `core` (the `GpuSchedulingGauge`
package is the precedent for a `core` type both halves see) listing each **recomposable
component** with: name; the **declared dependency set** (config keys it composes from); its
**applied version** (a hash of the applied values of exactly those keys); its **compose mode
capability** (`beside`, `in-place`, or `chooses per apply`); a **start deadline**; a
**local-recovery attempt budget**; its lifecycle state (`composed`, `reloading`, `failed`,
`unavailable`, `absent`); last error; and an evidence pointer. Three components register at D1:
the **inference surface** (ORT encoder sessions: embed, SPLADE, NER, rerank, BGE-M3), the **index
runtime** (`RunningRuntime`/`RuntimeSession` behind `KnowledgeServer`), the **generative backend**
(`InferenceLifecycleManager`). The registry is a `core`/`app-api` interface bound in `EngineRoot`
so the worker half and the front register into one instance (two registries would each hold half
the truth, the C1-5 argument). It is also the producer for C1-12's `attempted configurations`
and `co-resident encoders` kinds.

**Acceptance:** a coverage test asserts every component the root wires with a config dependency
is registered (a scan over `EngineRoot`'s composition with an explicit exception list and a
vacuous-pass floor of 3); a test asserts a component's applied version changes when a declared
key's applied value changes and **does not** when an undeclared key changes (the dependency-scoped
coherence clause of 16's reconfigure row; the second half is the one a global hash fails);
`:modules:core:test`, `:modules:app-engine:test` green.

### D1-2 — `generation-bound` and `restart required` in the config register; the applied revision computed

Design 7.4 ("the config register marks such settings `generation-bound`"; "settings that need a
process restart … `restart required`"; the last paragraph: the applied version is **computed**).
There is no register file today (§0.7): D1 adds `governance/config-apply.v1.json` — one row per
apply-able key with `applyScope ∈ {hot, component:<name>, generation-bound, restart-required}` —
consumed by the `config-surface` gate (`scripts/governance/gates/config-surface/enforcer.mjs`)
as a second input beside `config-lifecycle.v1.json`, with a rule that every key in the generated
303-row matrix has a scope (the vacuous-pass floor is the matrix's row count). The
`generation-bound` set at D1: embedding model, SPLADE model, NER label set, chunking parameters,
BGE-M3 model (every input of `IndexFingerprint.Inputs`, `:213-224`). The `restart-required` set:
the JVM launch flags and the data directory.

The **applied configuration revision** (7.4, last paragraph) is computed, never stored: a hash
over the apply-able keys' applied values (from the registry, D1-1) plus the active generation's
recorded generation-bound settings (`IndexFingerprint` read from the active generation's commit
user data, `COMMIT_META_KEY` `:101`). The triple that may serve is *(applied apply-able version,
active generation id, journal high-water mark)*. C2-6's **global accepted-settings revision** is
a different number (the user-facing counter of accepted settings) and stays as C2 built it; the
component map (D2) shows both under different names.

**Acceptance:** `node scripts/governance/run.mjs --gate config-surface --mode gate` green with the
new register and reds on a key with no scope (verify the bite, revert); a test asserts the
computed revision changes when the active generation changes and is identical for two Engines
with the same applied values and generation; the encoders composed at boot are chosen from the
active generation's `IndexFingerprint`, asserted by booting over a generation whose metadata
names model X while the desired settings name Y and observing X composed with the desired value
reported as pending (the "index tells the encoders what to be" rule).

### D1-3 — reconfigure as an operation, and "only success persists"

Design 7.4 (the invariant paragraph; "two records, not one"). A `reconfigure` operation on the
operations port (C2's table gives it a row, a client key, and the global revision it was issued
against for `version conflict`): resolve the affected components from the declared dependency
sets (D1-1); write the **attempted-version record** (desired values, the component list, the
time) to `<dataDir>/config/attempted-version.v1.json` — a new store-recoverability row
(`EPHEMERAL`, `RESET`, owner `HEAD`, a free addition under C2-1's rule) — **before** the first
compose; compose each affected component in the mode D1-6 chooses; on full success write the
new applied values through `UiSettingsStore` and rebuild `ConfigStore`, clear the attempted
record, complete the operation with the per-component modes and reasons in its result; on any
compose failure close the candidates already composed, keep A applied, persist nothing as
applied, fail the operation with a reason naming the component, and leave the attempted record
so a restarted Engine can report "B was attempted and failed with <reason>" (the native-crash
case). `SettingsController.handleUpdateSettingsV2` becomes the HTTP front of that operation
(a settings write that touches no component's dependency set still goes through it and
completes at once). **`ConfigStoreRebuilder.rebuild`'s swallow (`:82-84`) is deleted**: a rebuild
failure is the operation's failure.

**Acceptance:** a test drives a two-component reconfigure where the second compose is made to
fail and asserts: the first candidate is closed, `ConfigStore` still holds A, `ui/settings.json`
is byte-identical to before, the attempted record names the failing component and reason, the
operation answers `failed` with that reason — *asserting only the response body is not the
acceptance; assert the settings file and the store*; a test asserts a rebuild failure surfaces
as the operation's failure and never as a 200; a test asserts a settings change that touches no
declared dependency leaves every component's applied version unchanged (`design 16` reconfigure
row); `check-store-recoverability` green with the new row; `--gate operation-surface` green with
the reconfigure surface registered (`consumesProjection` of C2's record).

### D1-4 — the generative backend's compose obeys the rules

`InferenceLifecycleManager.applyConfig` (`:650-824`) is the generative component's compose. Fix
the three departures from 7.4 (§0.8): validate VRAM **before** stopping the server, so
`INSUFFICIENT_VRAM` is a rejection that leaves the incumbent serving (the beside rule for a
component that cannot compose beside: refuse before closing); `applyConfigRollback` reports
success when the rollback restored A (`:867-871`) and failure only when it did not; the
`config = newConfig` assignment moves after a successful health check (`:755` today precedes it).
A surviving llama-server is adopted only when its `declaredConfigHash` matches A (B12) — already
so; the test here asserts it on the reconfigure path.

**Acceptance:** tests for the three cases (VRAM rejection with the server still answering;
rollback success reported as success with the operation still `failed`; the config field never
observed at B while the server is down) against a fake `serverOps`; the existing
`InferenceLifecycleManagerExternalServerTest` and `InferenceLifecycleManagerIdentityTest` green.

### D1-5 — the candidate footprint per model, and the device-memory port

Design 7.4 ("a field no model catalog entry carries today and D1 adds"). `model-registry.v2.json`
gains `runtimeFootprintBytes` per encoder model (the ORT session's measured device footprint at
its configured batch; `minVramBytes` stays the install gate), modelled on `ModelPackage`. Free
device memory reaches the session-assembly path through a new port in `app-api`,
`DeviceMemoryPort { long freeBytes(int device); }`, implemented over `GpuCapabilitiesService`
in `app-services` and bound by the root — because `ort-common` and the worker modules cannot
depend on `gpu-bridge` (§0.10). `ModelSessionPolicy.Gpu.arenaCapBytes` stays the device-side
arena cap and is named as such in the memory budget document (C1-13).

**Acceptance:** a test asserts every encoder model in the registry declares a footprint (a
vacuous-pass floor of the registry's encoder count); the port's implementation is exercised
against a fake `GpuCapabilities` snapshot and the `nvidia-smi` fallback; the registry's schema
test (`model-registry` has one; find it) green; `regen-all --check` green if the registry is in a
generated set.

### D1-6 — beside or in place, chosen per apply, and encoder A recomposed on rejection

Design 7.4 (continuity paragraph). For the inference surface: compose **beside** when the
candidate's declared footprint plus the margin (§2) fits `freeBytes`; otherwise **in place**
(close A's sessions, compose B, semantic legs `reloading`). The choice and reason go into the
operation result and the component map. On an in-place rejection the state is *applied A,
component `unavailable`* with the rejection recorded, and **recompose A** runs immediately as
the last step of the failed operation; if that fails too, the component stays `unavailable` with
both reasons and the stuck-component policy (D1-13) owns it. The index runtime composes beside
only as a second generation directory (D1-7); the generative backend is restarted, not
duplicated (D1-4).

**Acceptance:** four tests with the device line faked: beside chosen when it fits and A serves
throughout (a search on A answers during B's compose); in place chosen when it does not, with
`reloading` reported and text search answering; in-place rejection recomposes A and reports it;
in-place rejection plus A's recompose failing leaves `unavailable` with both reasons and hands
over to D1-13 (asserted by the recovery attempt count). *A test that only asserts the mode
string is not the acceptance; assert that a query during the transition gets the answer the
mode promises.*

reindex operation's row (C2-10). Live cursors on the old generation are D2's (`cursor expired`);

### D1-8 — the journal, replay, gaps, and the flipped default

Design 7.4 (capture and replay; activation atomic and conditional); 7.5 (converging operation);
C2-10 (the row, plan, two lists); §0.3, §0.5. The journal is the `switch_buffer` gate widened:
`IngestSwitchBufferOps.isSwitching()` (`:63-76`) becomes `isJournalling()`, true for `MIGRATING`
and `SWITCHING`, so every accepted write during the rebuild goes to Blue **and** to the buffer,
keyed to the reindex operation's id; replay before activation is the existing drain
(`drainSwitchBufferBestEffort` `:427-839`) run into Green after the enumerator finishes and the
embedding-drain gate (`:226-232`) passes. **Gaps** are computed at activation: units whose latest
accepted version is absent from Green (a failed replay entry, a failed unit whose document was
not superseded); **processing history** (failed then superseded, `superseded`) never counts.
Activation proceeds only with **zero gaps or a user's acceptance** (D1-10). The default
`max_failed_jobs` flips to **0** at `ResolvedConfigBuilder.java:1503` and `KnowledgeServer.java:202`;
an unreadable failure count is a **refusal**, not 0 (`:198-202`). A refused activation is
`complete with gaps` on the operation's row with the gap list, Green stays on disk as the
candidate, and **encoder A is recomposed immediately** (D1-6's rule; in the in-place mode the
semantic legs return on A); on cancel or attempts exhaustion the candidate directory and its
journal entries are deleted through `abandonBuildingGeneration` and `pruneMarkedForDeletionBestEffort`
(`:1004-1040`, given its first production caller), which is also the enforcer of "two generations
on disk" (C1-12's kind gets its producer here).

**Acceptance (the 16 generation-transition row's clauses as tests):** a reindex started, then an
edit, a removal and a new document accepted during the rebuild, activates with all three
reflected and the removed one absent; a reindex with one unit failed and not superseded refuses
with the gap named and the row `complete with gaps`; a document captured at H1, changed to H2 and
replayed at H2 is `superseded` and does not block (`design 7.5`'s clause, the one an
implementation from the older text gets wrong); an unreadable failure count refuses; after a

disk; after cancel it is not, and the on-disk generation count is 2 at most (asserted); `JobQueueMigrationTest`
green if the buffer's schema gains the operation id column (a ladder step, C2's shape).

## 11. Decisions recorded for D1 (design section 0, 2026-09-09)

- The journal is the widened `switch_buffer`, keyed to the reindex operation; not a new store.
- Activation is open-beside, swap, drain-and-close; the migration's requested restart is deleted;
  the requested restart stays for restart-required settings and the essential-component escalation.
- The essential-component escalation exits with a new code 5 (`ESCALATED_RESTART`, transient,
  counted).
- The config register is a new `governance/config-apply.v1.json` read by the existing
  `config-surface` gate; the applied revision is computed, the attempted record is a new
  `EPHEMERAL` store.
- Gap acceptance is the one route where the declared client kind carries a decision, because the
  owner assigned it to a person; it is refused for every other kind.
- Free device memory reaches session assembly through an `app-api` port bound by the root.
- Start deadlines: `index` 60 s, `encoders` 120 s, `generative` 180 s, from the PR 0 baseline;
  local budget 2; immediate escalation for corrupt store, native crash, out-of-memory.

Open on first contact (record in §0.1): whether `RunningRuntime.drainAndClose`'s "close anyway on
timeout" (`:203-211`) is acceptable during a live swap or must become a refusal that keeps the old
runtime serving; whether the switch buffer's payload shape carries enough to replay a removal
issued during `MIGRATING` (today `DELETE` entries are applied directly at drain, `:463-546`).

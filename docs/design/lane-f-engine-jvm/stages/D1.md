# Lane F stage D1 — reconfigure, generations, readiness: implementation checklist

Written from the three inputs 17.6 requires: the stage's row in `design.md` 17.3, `verified-facts.md`,
and a fresh code-verified read. First drafted 2026-09-09 at `be47faa40` (the stage B head) and
**rewritten 2026-09-10 at `90843f475`** (the C1 head `4229f1091` plus the C2 design commit) after
four read-only audits re-resolved every citation by content; the audits are preserved verbatim in
[`evidence/D1/regrounding-2026-09-10.md`](../evidence/D1/regrounding-2026-09-10.md) and every
`file:line` below is at `4229f1091` unless it names a C2 document. `design.md` is cited by section.
C2 lands before D1 and its contract with D1 is in
[`evidence/C2/operations-store-design.md`](../evidence/C2/operations-store-design.md) §1.3 to §1.8;
this checklist cites it and re-decides nothing there.

Stage D1 in one line (17.3 row D1, as amended 2026-09-10): **one Engine component model that is
both the recomposable registry and the readiness authority; reconfigure as an operation whose
components compose through it with "only success persists"; live generation activation in two
flows, Flow A (same encoders, replacing today's restart at cutover) and Flow B (a generation-bound
change, encoder set B beside or in place of set A); start deadlines, local recovery and bounded
escalation on the component model; the reason-code vocabulary re-cut; the harness that feeds E's
lifecycle rows.**

### D1-1 — the Engine component registry: one substrate for recomposition and readiness

Design 7.4 (recomposable registry), 7.6 (readiness by component), 3.2 (core interface, root
binding). A contract in `core` (`io.justsearch.core.component`, beside `core.execution`),
implemented in `app-engine`, constructed in `EngineRoot` as a field beside `executors`
(`EngineRoot.java:52-55`) and handed to the index half through the widened `serverFactory`
(`:88-89`, `:199-201`) and to the front at `:249-251`. The precedent is `EngineExecutorRegistry`,
including its typed refusal shape, its sorted immutable snapshot and its policy loaded from the
classpath-staged `retained-state.v1.json`; **not** `GpuSchedulingGauge`, which is created in
`KnowledgeServerBootstrap` (`:102-103`) and carries no lifecycle.

Contract: `register(ComponentSpec) -> ComponentHandle`; `snapshot()`; `applyLock()` (one
`ReentrantLock` with `tryLock`, the attempted-configurations permit); `close()`. A spec carries
`name`, `essential`, `dependencyKeys` (config keys), `composeCapability`
(`BESIDE | IN_PLACE | CHOOSES_PER_APPLY`), `startDeadline`, `recoveryBudget`. A handle carries
`state` (`ABSENT, STARTING, READY, RELOADING, FAILED, UNAVAILABLE`), `reasonCode`,
`stateSince` (wall and monotonic), `appliedVersion`, `desiredVersion`, `lastCompose`
(mode, reason, free bytes, footprint), `recoveryAttempts`, `evidence`; `transition(...)`,
`setAppliedVersion(...)`, and listener registration for the projections of D1-2. Four
components register: `api` (front), `index` (`KnowledgeServer`), `encoders` (the serving
`EncoderSet`, D1-12; at D1-1 the existing surface), `generative` (`InferenceLifecycleManager`).
The registry activates `attempted-configurations` from the apply lock. D1-9 activates
`representation-generations` when its live accounting exists, and D1-12 activates
`co-resident-encoders` when encoder sets exist; declaring the component model does not
activate either future producer.

**Acceptance:** a coverage test asserts every component the root wires with a config dependency
is registered, with an exception list and a vacuous-pass floor of 4; a test asserts a component's
applied version changes when a declared key's applied value changes and does not when an
undeclared key changes; a test asserts a second `applyLock` holder is refused and the
`attempted-configurations` snapshot count reads 1 while held; `EngineResourcePolicyTest:25-38`
updated only for the producer activated by this item (it is the drift check); `:modules:core:test`,
`:modules:app-engine:test` green.

### D1-3 — the config-apply register, applied versions, and "the index tells the encoders what to be"

Design 7.4 (generation-bound, restart-required; the applied revision is computed). A new
`governance/config-apply.v1.json` with one row per `EnvRegistry` key:
`applyScope ∈ {hot, component:<name>, generation-bound, restart-required}`. Its **semantics**
live in `ConfigApplyRegisterTest` in the `configuration` module: every registry key has exactly
one row, every row names a registry key, every `component:` name is one of the four, and
generation-bound rows equal the set of keys that feed `IndexFingerprint.Inputs` (embedding,
SPLADE and NER model selection; the vector format and HNSW inputs). The `config-surface` gate
ratchets a fourth scalar (`applyScopeCount`) and nothing more, because it reads a gitignored
JSON (§0.12). Chunking parameters are constants and get no row; the register's `note` says
they are generation-bound by construction. The restart-required set is the data directory
and the launch flags the launchers own.

Applied version per component = SHA-256 over the canonical JSON of the applied values of its
declared keys, set on the handle at compose. The applied configuration revision = SHA-256 over
every component's applied version plus the active generation's fingerprint inputs
(`COMMIT_META_INPUTS_KEY`, `IndexFingerprint.java:110`). C2's accepted-settings revision is a
separate counter (`operations-store-design.md` §1.8) and is what version conflict compares.

**Acceptance:** `ConfigApplyRegisterTest` reds on a key with no row and on a row with an
unknown key (verify both bites, revert); `--gate config-surface` green with the fourth
scalar; a test asserts the computed revision changes when the active generation changes and is
identical for two engines with the same applied values and generation. The generation
manifest/model-binding work and its boot tests belong to D1-12 (batch4), not this item;
batch1 must not claim that behavior from the register declaration.

### D1-4 — `core.reconfigure`, and "only success persists"

Design 7.4 (invariant; two records), 7.5 (a reconfigure is an interactive turn), 7.6 (version
conflict); C2 §1.5 (`recordKind = reconfigure`, the executor delegates to the sole attempt runner, the handler gets an
identity/checkpoint-only record handle), §1.8 (the revision port). A catalog operation in `CoreOperationCatalog` with
input `{settingsPatch, expectedRevision}`, bound in `OperationHandlerRegistrations`, dispatched
through `OperationExecutorImpl.dispatchCore` (`:619-630`) with the context the front resolved.
Admission is the HTTP front's (the executor has no seam, §0.13); the handler attaches the
admitted work so shutdown step 2 cancels it.

Handler flow: refuse `VERSION_CONFLICT` through the revision port; partition the patch by
`applyScope`; **generation-bound keys are refused** with `GENERATION_BOUND_REQUIRES_REINDEX`
naming the keys and `core.bulk-reindex` as the operation that applies them (explicit, never
chained); restart-required keys are persisted as desired through the revision port and the
requested restart is scheduled after the row completes (D1-6); `hot` keys apply through the
config store; component keys are grouped. Take `applyLock` (refuse `RECONFIGURE_IN_PROGRESS`);
the reconfigure row in `RUNNING` **is** the attempted record (*reversal of the 2026-09-09
"new EPHEMERAL store", section 0 2026-09-10*: a durable row already survives the crash, and a
second file would be a second authority); compose each affected component through its handle
in the mode D1-14 chooses, using C2's serialized settings transaction and prepared
publication protocol (operations-store-design.md section1.8). All fallible preparation and
composition precedes the settings-file commitment point. Before commitment, failure or
cancellation closes candidates, recomposes A for in-place components, persists nothing,
and fails the row naming the component. After commitment, publish only prepared references
and let the runner complete from the committed receipt before clearing the settings fence;
a post-commit outcome-write
failure is recovered as committed, never mislabeled FAILED. The bounded settings witness
reconciles a matching interrupted row to COMPLETE; only an interrupted pre-commit attempt
becomes FAILED/ENGINE_RESTARTED_DURING_APPLY. Prove component installation needs no
fallible allocation/validation after commit; retire the old apply-then-rebuild sequence.
The component view reads "last attempted" from the latest reconfigure row.

`SettingsController.handleUpdateSettingsV2` (`:104-153`) becomes a thin front that dispatches
the operation and maps its outcome (`200` complete, `409` version conflict, the failure channel
otherwise); the `chatEnabledChanged` nudge (`:142-145`) becomes a generative-component
dependency. `core.reload-inference` and `AdminInferenceReloadHandlers` are retired into it
(`retire-with-a-sweep`); `RuntimeActivationService`'s install-time apply (`:1130`) composes

## 11. Decisions recorded for D1 (design section 0, 2026-09-09 and 2026-09-10)

- The journal is the widened `switch_buffer`, keyed by the building generation id; not a store.
- Activation is a re-point of the already-open Green under `runtimeSwapLock`, with a bounded
  drain of Blue that retains on timeout; the migration's requested restart is deleted; the
  requested restart stays for restart-required settings and escalation.
- The essential-component escalation exits with code 5, transient, counted.
- One component registry in `core` is both the recomposable registry and the readiness
  authority; the envelope, the snapshot (schema 2) and the manifest lifecycle are its projections;
  `Capability` is its `app-api` adapter.
- `governance/config-apply.v1.json` with a JUnit semantics test and a fourth ratcheted scalar;
  the applied revision is computed; the attempted record is the reconfigure row (*reversal of
  the 2026-09-09 EPHEMERAL store*).
- Gap acceptance is a keyed `accept-gaps` operation refused for every kind but the webview.
- The device line is a `core` supplier bound in the root; the footprint is the arena caps; one
  ceiling key simulates the floor.
- Encoder sets are generations; fingerprint model identity is per runtime; the generation
  manifest records the models a generation was built with, and boot composes from it.
- Native quiescence is per-handle lease accounting with retire-and-retain.
- The previous generation is pruned when its runtime closes after activation, so design 8's two
  generations on disk holds; no directory rollback after activation.
- Generation-bound keys are refused by reconfigure and applied only by an explicit reindex.

# Lane F stage C1 — context and resources: implementation checklist

Written from the three inputs 17.6 requires: the stage's row in `design.md` 17.3,
`verified-facts.md`, and a fresh read of the code. Drafted 2026-09-08 at `e692b86ef` (stage B
items B1-B6 landed) and **re-grounded 2026-09-09 at `be47faa40`, the stage B completion head**,
by a code-verified pass: every `file:line` below was re-resolved by content at that commit (the
grounding facts are recorded in the commit body of the re-grounding); a claim that did not survive
is corrected in §0 rather than silently rewritten. `design.md` is cited by **section** (it was
consolidated after the draft, so its line numbers are not stable); code is cited by `file:line`
at `be47faa40`. Section numbers are `design.md`'s unless prefixed with a letter.

The seven questions the draft raised are **decided** in `design.md` section 0 ("Stage C1 and C2
checklists drafted during B; their questions decided", 2026-09-08) and one more on 2026-09-09
(the `ForegroundLoad` producer cut, C1-10); §11 lists the decisions in one line each and the
items are written to them. The implementer does not re-open them.

Stage C1 in one line (17.3 row C1): **the engine context with its two axes threaded through the
ports, provenance at the grant store slot plus the ledger column and request attribute, admission
per context at the front with aggregate caps and reason codes, admission as the `ForegroundLoad`
producer, the executor registry with bounds and the no-common-pool rule, the retained-state
register, the memory budget lines and `MaxDirectMemorySize`, and section 6's attack-surface pins.**

2. **"None has a fixed thread count" is wrong; the unbounded thing is the queue.**
   8 says "Every named executor has a fixed thread count and a bounded queue (none does today)"
   (`design.md §8 (aggregate envelope)`, corrected by 17.9 item 15). At this HEAD there are **56** construction
   sites in `modules/*/src/main` (`Executors.new*` / `new ThreadPoolExecutor` /
   `new ScheduledThreadPoolExecutor` / `new ForkJoinPool`; the design said 58 — the drop is stage
   A's deletions), and they break down: **41** `newSingleThreadScheduledExecutor`, **8**
   `newSingleThreadExecutor`, **4** `newVirtualThreadPerTaskExecutor`, **2** `newCachedThreadPool`,
   **1** `newFixedThreadPool`. Forty-nine of fifty-six therefore already have a fixed count of one.
   What none of them has is a **bounded queue** (every `Executors.new*` factory hands back an
   unbounded `LinkedBlockingQueue`) or a **registration**. The three genuinely elastic pools are
   `OnlineModeOps.java:96`, `PersistentExtractionSandbox.java:172` (both cached) and
   `PdfOcrEngine.java:221` (fixed, sized from a config). This makes C1-5/C1-7 much smaller than the
   design's sentence implies, and it moves the real risk from "thread explosion" to "a queue that
   grows until the heap does" — which is the failure the memory row of 16 would actually see.

3. **The `ForegroundLoad` producer cannot be at the API front, and must not be a second one.**
   17.3's C1 row says "admission as the `ForegroundLoad` producer (8)" and 8 puts admission at the
   API front (`design.md §8 (admission)`). Two facts block the literal reading, both load-bearing:
   - `ForegroundLoad` is `io.justsearch.indexerworker.loop.pacing`
     (`modules/worker-services/src/main/java/io/justsearch/indexerworker/loop/pacing/ForegroundLoad.java:2`),
     a package ArchUnit **rule 6b** closes to everything outside `io.justsearch.app.engine..`,
     `io.justsearch.indexerworker..` and `io.justsearch.adapters..`
     (`modules/app-launcher/src/test/java/io/justsearch/app/launcher/LayeringEnforcementTest.java:203-227`,
     `onlyEngineAndWorkerMayDependOnWorkerInternals`). `modules/ui` — where the front filters live —
     may not name the type. This is the same edge that made B4's "re-home both halves" impossible
     (`stages/B.md` §0.1); `EngineShutdownSequence.java:29` records it in code.
   - `ForegroundLoadGate` already wraps the search calls at exactly one layer and says in terms that
     a second wrap is a defect: *"It is not reentrancy-safe, and must not be… the caller wraps at
     exactly ONE layer: `EngineKnowledgeClient.executeSearchRpc`… Do not add a second wrap deeper
     in"* (`modules/app-engine/src/main/java/io/justsearch/app/engine/ForegroundLoadGate.java:48-53`;
     the wrap is `EngineKnowledgeClient.java:351`, the gate is built at `EngineRoot.java:210`).

   So C1 **moves** the producer, it does not add one, and it moves it through an interface the core
   defines and the root binds (3.2's rule, `design.md §3.2`). Stated as an addition, this item
   would double-count every search and over-throttle indexing — which is the exact defect
   `ForegroundLoadGate.java:61-73` records as the `wrong-gate` case from stage A.

### 0.1 Corrections found while implementing (appended per item)

- **C1-2/3 propagation scope (2026-09-09):** explicit context reaches document access, agent
  runs/tools, conversation runners, operation dispatch/undo, pending approvals, diagnostics and
  status cache misses as well as the two named ports. These are actual producers or forwarding
  seams of port work, not independent context authorities. Async callbacks capture context;
  resumes and forks retain the current caller's authority and create a new run correlation id.
  App-side `OnlineAiService` calls do not cross the index port: their inference scheduling remains
  measured by `GpuSchedulingGauge`, as §11 anticipated, rather than a second `ForegroundLoad`
  producer. This is not a claim that every inference API accepts EngineContext.
- **Front attribution (2026-09-09):** HTTP/MCP resolves one request attribute after security
  filters. Client labels remain cooperative accounting metadata. Front requests choose
  INTERACTIVE/FOREGROUND; headers cannot select lifetime or urgency. MCP forces its registered
  source regardless of headers. Browser operation replay already forwards AGENT_LOOP/WORKFLOW/
  LLM_EMISSION/MCP, so these retain their registered UNTRUSTED tier. Browser SYSTEM_INTERNAL
  normalizes to BUTTON; only actual internal producers assert SYSTEM_INTERNAL. Unsupported
  scheduled/plugin sources fail validation. Agent/workflow/LLM child work rebases transport and
  tier through the source catalog while preserving caller identity and explicit axes. Durable
  operation admission and foreground detachment remain required batch 3 work (C1-11).
- **C1-4 projection ownership (2026-09-09):** a two-string `JobQueue.EnqueueProvenance` value
  rides the existing CallContext and enqueue entry. The Engine bridge projects originator via
  the existing `ActionLedgerProjection.originatorOf` authority; Worker persists the value without
  an upward dependency. Compared with moving the transport registry into core, duplicating its
  string switch in Worker, or widening every ingest payload, this keeps the existing authority
  and one bridge projection. WORKFLOW is corrected to the agent originator alongside AGENT_LOOP.
  Claim snapshots carry provenance through IndexJob, ExtractedJob and LedgerEntryFactory. The
  original proposal to look up the current row at terminal write was refuted by concurrent
  re-enqueue: caller B can replace the row while caller A is processing. Carrying the immutable
  claim value fixes attribution without a new marker, generation or state machine. Explicitly
  unknown legacy claim attribution stays null; only contextless queue operations may recover
  current-row attribution. Null maintenance enqueue preserves prior admission. Versioned
  SWITCHING payloads retain collection and attribution; explicit sync requests must do so too.
- **Sync replay and request logging review corrections (2026-09-09):** normal and buffered sync
  now retain explicit admission attribution; only INTERNAL plus SYSTEM_INTERNAL is maintenance,
  so a CLI caller using SYSTEM_INTERNAL still records a new explicit admission. The existing sync
  helper carries a nullable queue projection; its replay entry executes internally with the saved
  descriptive projection, avoiding either a fabricated EngineContext or persisting a second full
  context representation. Versioned UPSERT/SYNC_ROOT payloads require their emitted fields,
  including explicit null attribution; legacy payloads remain readable without invented metadata.
  Malformed payloads remain durable. The existing HTTP completion span reads the cached context
  and exports only engine.originator/engine.transport through the telemetry allowlist; client,
  session and grant identifiers are excluded from that projection.
- **Buffered maintenance coalescing (2026-09-09):** the generic switch-buffer replacement
  could erase an explicit sync admission before it reached jobs. `putSyncRoot` now coalesces
  under the existing SQLite queue lock: incoming null maintenance preserves previous provenance
  while retaining incoming root/force; explicit admission replaces it. The shared
  `SwitchBufferSyncRoot` codec replaces the duplicated writer/replay JSON shapes and supplies
  coalescing's parser, beside the existing UPSERT codec. Compared with a front-side read/put pair
  (racy), new keys/state (unnecessary), or a second parser (drift), this keeps one durable row and
  one representation. Generic opaque-buffer replacement is unchanged; unreadable prior sync
  work refuses maintenance instead of being erased. Reopen/replay and mutation regressions prove it.
- **Batch-3 preparation findings (2026-09-09):** `CallContext.CancelSignal` is Worker-internal
  and cannot be exposed to the front. C1-8 needs a neutral admission/cancellation handle whose
  first-wins reason is adapted at the Engine boundary. C1-10's single accounting owner must cover
  unary ingest and streaming work as well as executeSearchRpc; the literal search-only placement
  cannot satisfy its non-search acceptance. Composition currently forks Engine startup before
  ServicePhase creates operation leases, so batch 3 must establish the shared owner before that
  fork. These corrections preserve the decided urgency key, one gauge and existing trust boundary;
  their detailed binding and live proof belong to batch 3 below.
- **Batch-3 exact work ownership (2026-09-09):** design 3.4 now adds an optional, Engine-minted
  in-process work id to EngineContext. Neither context equality nor client/session identity can
  safely identify one waiting work item. The existing required cancellation registry resolves
  this id to a neutral lifecycle handle, preserving it through rebases and refusing stale ids.
  It is separate from C2's persisted client operation key and carries no authority. This is the
  smaller explicit carrier than a second wrapper/parameter across every port; no ThreadLocal
  context carrier or equality-keyed work registry is allowed. A thread-local nesting assertion
  at the gauge is permitted; it carries no context. Production operation leases already maintain
  process-local freeze without disk; their stale no-op documentation must be corrected.
- **Batch-3 control-plane freeze (2026-09-09):** `/api/upgrade/*` is subject to normal capacity
  accounting but bypasses only the new frozen-state refusal, so prepare can be followed by
  status, cancel and commit. Health bypasses all resource admission. The two front filters
  remain separate. Prepare retains its mutation-lease cancellation; only ordered shutdown
  cancels interactive front handles, avoiding cancellation of the prepare request itself.
  Existing conversational runs continue after an observer disconnect; C1 must preserve that
  behavior. C1-11 detaches durable foreground urgency; C2 owns its persisted operation row.
- **Batch-3 fairness and ownership (2026-09-09):** the quota key is `(clientKind, clientId)`;
  changing sessions, grants, transport, source tier, work ids or axes cannot partition that quota.
  Frozen refusal precedes capacity refusal; aggregate exhaustion precedes client exhaustion when
  both apply, because no caller can consume another aggregate slot. Attached views may rebase
  attribution but survival and effective urgency remain work-owned. Background scheduling creates
  fresh child work at execution; pending approval reserves fresh child work before consuming the
  pending record, preserving its original attribution and exact invocation provenance.

- **Batch-3 model lifetime and first reason (2026-09-09):** OnlineAiService.StreamRequest borrows
  the neutral work handle; producer and callback pump retain independently until actual exit.
  Cancellation interrupts the producer and closes its HTTP body; terminal follows the active
  callback. Conversation, agent and hierarchical turns retain across post-model finalization.
  AgentError adds optional reasonCode and persisted CANCELLED is an explicit terminal state,
  preventing cancellation from parsing as READY_FOR_LLM. A second model registry or persistent
  cancellation marker is unnecessary because the admitted work already owns identity and reason.
- **Batch-3 managed SSE (2026-09-09):** the writer owns a pre-created completion future and one
  composed close callback installed before writes. Local Javalin 6.7.0 bytecode proved keepAlive
  can create its future after one-shot close, stranding the request. The public Context.future
  API preserves completion even before installation. Late replay subscriptions close after a
  concurrent disconnect. Controller retention covers actual run return; disarming before normal
  retirement prevents a false durable background transition. Retirement registration and snapshot
  share the existing listener lock, with callbacks outside it. A mutation test fails the old
  check-then-add race; real HTTP durable disconnect and normal retirement tests pass.
- **Batch-3 refusal projection (2026-09-09):** only pre-execution REST refusal carries retrySafe
  true; approval child admission happens before pending consumption. Mutation-lease freeze on
  MCP now defers its already-decided refusal to the JSON-RPC owner so request ids survive and
  notifications remain silent, even if freeze clears between filters. Later errors cannot enter
  the webview's admission retry loop. Capacity responses carry Retry-After; upgrade waits use the
  existing default delay when the server supplies no hint.

- **2026-09-08, batch 1 grounding at 739d58020; integrated design at 395078f04.** Two independent
  read-only audits confirmed twelve bare async calls but **58 executor construction sites**,
  including the two bounded `SynchronousQueue` pools in `EngineKnowledgeClient` (133,145).

### C1-9 — the aggregate cap, and why it is a different rejection

Design 8 (`design.md §8 (aggregate envelope)`). The executor registry and the session gate are the aggregate
envelope. When an aggregate cap is reached the front rejects **regardless of the context's own
headroom**, with the same reason code and retry-after shape as C1-8 — 8 is explicit that the two
schemes are named apart (per-context admission decides *who waits*; the caps decide *how much
runs*), so the reason code must say which one fired or the aggregate-bound row of 16 cannot be
read.

**Acceptance:** the aggregate-bound row's first clause, as a test: N contexts each inside their own
limit, N times that limit above an executor's cap, and the rejections carry the **aggregate**
reason code while the executor queue never exceeds its bound; **and the same offered load from one
context rejects the same number**, which is the clause that shows the bound is independent of client
count and is the one a naive implementation fails. A per-context-only implementation passes the
first half and fails the second — do not report the first half as the row.

### C1-11 — urgency held by the work item, and the flip to background

## 7. The harness the checkpoint proof needs

The proof is *"a scripted agent loop hits admission and gets reason codes, never timeouts"*
(`design.md §17.3`).

**Where it lives.** `scripts/jseval/lane-f/`, beside the lane's existing instruments
(`head-flag-run.sh`, `encoder-latency-probe.sh`, `fixture-cycle.sh`, `head-rss-sampler.ps1`,
`analyze-head-run.cjs`) — the directory PR 0 created for exactly this class of thing
(`design.md §0`). Node or shell, driving the live stack over HTTP; it is not a unit test, because
the property is about a real front under real concurrency.

**Shape.** `admission-loop.mjs`, three parts:

1. **The driver.** M concurrent clients, each issuing a search-and-chat loop against the live
   stack with a declared engine context, offered load ramped until rejections appear. It reads the
   admission cap from the running Engine (the component map is D2's, so at C1 it reads it from the
   config it started the stack with) rather than hard-coding it, so the harness cannot silently
   drift from the value under test.
2. **The oracle.** Every non-2xx is classified: an admission rejection (429 + the reason code +
   retry-after) is a **pass**; a timeout, a 500, a connection reset or a 503 that is not the upgrade
   barrier is a **fail**. The verdict is the count of the second class being zero — *not* "we saw
   some 429s", which is the vacuous reading.
3. **The aggregate arm.** The same total offered load from one context, asserting the same rejection
   count (§C1-9's second clause). Both arms in one run, because the row is the pair.

**How it is bounded.** A hard wall-clock cap of **five minutes** per arm, enforced inside the script
(`process.exit` on the deadline with a `TIMED_OUT` verdict, so an over-run is a legible failure
rather than a hung agent), a fixed request budget, and no retry loop around the whole run. It runs
under a declared `leaseDurationSec` on the shared dev stack (the lease model exists for exactly
this: minutes of busy-but-silent work). **It is never backgrounded past an hour** — tracked
background tasks are killed at ~60 minutes and `TaskStop` does not reap child loops
(`agent-lessons.md`); a campaign that needs longer is E's, not C1's.

**Commands.** Exactly these, so the evidence record and the brief name the same thing:

```
# oracle self-test, no stack (batch 1); the script lives beside the other lane-f instruments under scripts/jseval/lane-f/
node scripts/jseval/lane-f/admission-loop.mjs --self-test
# live run (batch 3), from the worktree, under an orchestrator-owned stack lease
# The orchestrator starts/stops the owned dev runner with a declared lease and startup cap reduction.
node scripts/jseval/lane-f/admission-loop.mjs --capture <outdir> --base-url <owned-api-url>
node scripts/jseval/lane-f/admission-loop.mjs --analyze <outdir>          # exit 0 only on PASS for both arms; prints the counts
```

The per-context cap the harness asserts against is read from the stack's effective config
(`/api/debug/effective-config`, the same source PR 0b's fixture reads its pins from), never
hard-coded.

**Wiring.** The harness needs the live stack, so it is not a CI gate; it is the checkpoint proof,
run once and recorded under `evidence/C1/` with its raw counts beside the verdict. Its **oracle**,
however, is unit-testable without a stack, and is: a self-test feeds it a recorded transcript
containing one timeout and asserts the verdict is `fail`. Ship the self-test in the same commit —
an oracle that has never seen a failing input is an oracle nobody knows works.

## 13. Batch-4 implementation decisions (2026-09-09)

The source census is 58 inherited executor construction sites. The two EngineKnowledgeClient
SynchronousQueue pools already existed at the stage-B head; the original 56-site census omitted
them. LocalTelemetry additionally leaves OTel PeriodicMetricReaderBuilder to create a hidden
scheduled pool: inspection of the installed OTel 1.60.1 bytecode proves this 59th logical factory.
Four JDK HttpClient default cached executors also require injection (InferenceLifecycleManager,
ManagedChildReconciler, OpenAiCompatController, RuntimeActivationService).
Coverage must count logical registered factory sites after centralization (floor 63), and
separately reject raw constructors outside the implementation and named external-process exception.
A raw-constructor-only test would become vacuous when the implementation replaces the factories.

The neutral registry contract lives in core; its implementation and loaded policy live in
app-engine beside admission. EngineRoot supplies the same instance through application and
index-half construction. Logical registrations have unique names and explicit kinds. Replacement
and per-call instances are tracked separately from their logical registration; shutdown cannot
remove an instance from accounting while its thread is still alive. Bounds on repeated opens must
cover wedged TimeboxedContentExtractor replacements as well as ordinary queued tasks.

TimeboxedContentExtractor has one thread and at most two live generations: the active one and
one wedged predecessor. Shutdown alone never frees a generation slot. A second wedge makes the
current executor unavailable; subsequent work receives a typed capacity refusal until an old
generation actually terminates. The triggering extraction retains its truthful timeout outcome;
later refusals use the existing parser-failure retry/backoff path. This preserves one recovery
attempt without the current unbounded native-thread leak. OCR permits one live pool and caps auto
sizing at the policy's backgroundThreads (currently four); explicit larger worker settings fail
configuration validation instead of silently changing the requested value. These instance limits
express existing owner multiplicity, independently of the admission diagnostic override.

The model callback pump's ConcurrentLinkedQueue is also bounded in this slice. Its callback
buffer uses the foreground queue budget and reports typed overflow to the producer, which closes
the stream and reports failure after the active callback finishes. It must never block the model
read while holding the online-request lock, silently drop callbacks and report success, or retain
an unlimited queue outside the executor's own queue accounting.

Telemetry remains a foundation leaf and receives registered ScheduledExecutorServices, without
importing the registry. EngineRoot construction moves before Head telemetry construction. The
metric reader receives its own scheduler through PeriodicMetricReaderBuilder.setExecutor; it
cannot share the heartbeat scheduler because reader.close shuts its supplied executor down.
Composition correction: LauncherEnvironment constructs a full HeadAssembly, so an exception for
its two telemetry schedulers alone would leave many application executors outside policy. It
explicitly loads one EngineExecutorRegistry provider with ServiceLoader through its existing
runtimeOnly app-engine dependency, rejects missing/ambiguous providers, and owns that registry
through HeadAssembly and telemetry close. This follows the existing service-provider pattern
without moving JSON policy loading into core or adding a concrete launcher-to-Engine dependency.
The old BoundaryRulesTest selected io.justsearch.app.launcher while production uses
io.justsearch.applauncher; its effective package and existing composition allowance must be made
explicit before claiming it proves the launcher boundary.

EngineRoot's WorkerHost.close is also used for restartable index boot recovery. It must close
only current index/client instances, not the process registry or Head executors. The complete
process shutdown sequence closes the shared registry after the Head, index and telemetry owners.
Registration lifecycle must permit clean owner reconstruction without accumulating a new name
on every restart; a still-running retired executor remains accounted and cannot be hidden by a
new generation name.
Concretely, Registration.close marks it terminal, shuts down all its instances and waits one
bounded deadline outside the registry lock. Registration/snapshot prune a closed name only after
all actual instances terminate. An active duplicate remains an error; a closed but still-live
predecessor refuses new ownership with INSTANCE_LIMIT. This supersedes the initial, unnecessary
forever-reserved-name choice. It preserves the existing boot-recovery reconstruction graph and
keeps TimeboxedContentExtractor's two generations under one registration; an unkillable previous
owner requires process recovery rather than another unaccounted parser generation.

Scheduled work has two bounds: the executor's delayed queue capacity and the process-wide
256 timer registrations from the existing policy. One-shot permits release immediately before
callback execution, so a callback can rearm itself at the limit. Periodic permits remain held
until cancellation, failure or shutdown. Use ScheduledThreadPoolExecutor's decorateTask seam to
wrap its already-created RunnableScheduledFuture; this avoids a second delegate-install race.
The wrapper must remove itself from the delayed queue on cancel (the JDK delegate is not the
queued wrapper), release on rejection and shutdownNow, and detect periodic failure after run.
Actual running callbacks remain bounded by executor threads; timer registration is not a second
Engine admission credit. Refusal is typed and never a silent discard or caller-runs stall.

For delayed agent work, timer-submission refusal is synchronous. A future due-time executor or
admission refusal cannot be sent back on an already-completed HTTP request: C2's accepted operation
row owns that terminal outcome. Do not claim otherwise or add a C1 persistence authority.

Confinement retains VDU's named PDF-render exception and a separate build-time-only exception for
io.justsearch.ui.AotTraining. The latter loads exactly three Tika class names without static
initialization to train the production-classpath AOT cache; it never parses user files. Pin those
literal reflective references and their exact owner in a source assertion as well as the ArchUnit
dependency rule. Delete only the implicit broken-child-command fallback; retain explicit in_process
mode. The adverse extraction proof must fail all five routed families with SANDBOX_FAILED while
text, Markdown and CSV still extract in the same session.

Implementation slices: (1) registry contracts, implementation and lifecycle/bounds tests;
(2) root/telemetry and all producer wiring plus bare-async retirement; (3) extraction routing,
confinement and reflection pins; (4) residue sweep, rule mutation proofs, full stress-enabled
verification and fresh live admission/pacing against the final installed candidate. The C2

### 2026-09-09 partial fanout refusal and actual-exit ownership

An executor's live-instance count does not retain the admitted work. Returning promptly after a
later search-leg submission refuses would close the port's unary reference while an earlier leg
could ignore cancellation and remain alive. Waiting in ExecutorService.close preserves ownership
but hides that synchronous refusal indefinitely. A port-specific early-failure callback would keep
a worker stranded and couple lower search helpers to transport completion.

Use an explicit neutral child-lifetime factory in CallContext, backed by the existing work.retain
authority, and one ephemeral EngineTaskGroup per fanout. It counts actual-exit callbacks from
EngineFutures, cancels accepted children on leaving the group, and releases its one retained owner
after the group is sealed and all accepted children exit. No new admission catalog or ambient
context is introduced. Lower index fanouts must also retain their RuntimeSession resources until
actual exit; this must be proven before enabling prompt lower returns. ForegroundLoadGate supplies
an explicit child-lifetime factory from its existing call wrapper. For interactive work the one
pacing increment lasts through parent exit and every retained child exit; calls with no children
keep their existing per-call balance. Durable work keeps its existing completion/background
transition owner. Holding all interactive admission references until work completion was rejected:
it would alter sequential/concurrent port calls sharing a handle and the C1-11 per-call contract.
The single workId wrap guard remains, and a child never starts a second pacing increment.

Required proof includes aggregate limit one, a first leg ignoring interrupt, exact prompt refusal
from the next submission without replay, admission and foreground pacing retained until first-leg
exit, caller-interrupt parity, runtime-close safety, and 0/1/N accepted group cleanup. This decision
is being implemented; it is not a claim that these proofs already passed.

### 2026-09-09 KnowledgeServer producer ownership

The stuck-job reaper and deferred model initializer use dedicated singleton background
registrations: scheduled `index.stuck-job-reaper` and platform `index.deferred-model-init`, one
thread each with the existing background queue limit. They are server owners, not interchangeable
watcher/extraction generation slots. Reaper cancellation is followed by actual executor termination
before queue close; model executor termination precedes inspection of the exposed future and
closure of published native/runtime fields. Direct ExecutorService.close supplies that lifetime
boundary; no new state machine, marker or registry is needed. An interrupt-ignoring task can delay
close, but cannot cause its still-used resources to be closed underneath it. Focused proof and
mutations are in [server producer evidence](../evidence/C1/server-producers.md); C1 remains open.


### 2026-09-09 bounded scan observation ownership

Scan progress is cumulative observation, not the durable operation record. Keep one bounded
replay ring per scan (background queue policy), with cursor subscriptions reading that shared
ring rather than copied histories and independent queues. A subscriber overtaken by retention
receives UNKNOWN_SCAN_OR_RETENTION_EXPIRED; a new subscriber starts at the oldest retained event.
Completed entries expire after 30 seconds or are evicted oldest-first for a new scan. The total
entry cap is the aggregate work policy; if every entry is active, registration refuses with typed
capacity failure. Subscription count is bounded by the foreground queue policy and every HTTP
handler closes its subscription. Terminal delivery, interruption, idle expiry and registry close
release subscription ownership too. No persistence or second policy catalog is introduced.
This supersedes the unbounded full-history promise; final scan counts and the scan itself are not
altered by slow-observer expiry. Required tests cover each cap, lag expiry, terminal delivery and
slot reuse after close/interruption. Producer delivery must preserve typed refusal at its port.


### 2026-09-09 per-source fanout ownership correction

The inherited C1-7 table's single persistent foreground virtual pool is superseded by two stable
Head-owned virtual registrations, one per urgency, with per-call instances capped by the aggregate
work policy. HTTP and agent adapters borrow the same owner through reconnects. Per-call groups
reuse EngineTaskGroup's cancellation and actual-exit retention; a persistent shared executor would
require another non-owning group lifecycle. This avoids that extra mechanism and prevents durable
background searches from consuming foreground execution capacity. Attach the existing admitted
work before submission, retain it through actual child exit, propagate current work context into
child calls and wire work cancellation to accepted futures. Timeout, cancellation and capacity

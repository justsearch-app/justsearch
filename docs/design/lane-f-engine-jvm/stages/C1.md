2. **"None has a fixed thread count" is wrong; the unbounded thing is the queue.**
   8 says "Every named executor has a fixed thread count and a bounded queue (none does today)"
   (`design.md:1240-1243`, corrected by 17.9 item 15). At this HEAD there are **56** construction
   sites in `modules/*/src/main` (`Executors.new*` / `new ThreadPoolExecutor` /
   `new ScheduledThreadPoolExecutor` / `new ForkJoinPool`; the design says 58 — the drop is stage
   A's deletions), and they break down: **41** `newSingleThreadScheduledExecutor`, **8**
   `newSingleThreadExecutor`, **4** `newVirtualThreadPerTaskExecutor`, **2** `newCachedThreadPool`,
   **1** `newFixedThreadPool`. Forty-nine of fifty-six therefore already have a fixed count of one.
   What none of them has is a **bounded queue** (every `Executors.new*` factory hands back an
   unbounded `LinkedBlockingQueue`) or a **registration**. The three genuinely elastic pools are
   `OnlineModeOps.java:96`, `PersistentExtractionSandbox.java:139` (both cached) and
   `PdfOcrEngine.java:221` (fixed, sized from a config). This makes C1-5/C1-7 much smaller than the
   design's sentence implies, and it moves the real risk from "thread explosion" to "a queue that
   grows until the heap does" — which is the failure the memory row of 16 would actually see.

   17.3's C1 row says "admission as the `ForegroundLoad` producer (8)" and 8 puts admission at the
   API front (`design.md:1211-1234`). Two facts block the literal reading, both load-bearing:

     `io.justsearch.indexerworker..` and `io.justsearch.adapters..`

     `onlyEngineAndWorkerMayDependOnWorkerInternals`). `modules/ui` — where the front filters live —
     may not name the type. This is the same edge that made B4's "re-home both halves" impossible
     (`stages/B.md` §0.1); `EngineShutdownSequence.java:29` records it in code.
   - `ForegroundLoadGate` already wraps the search calls at exactly one layer and says in terms that
     a second wrap is a defect: *"It is not reentrancy-safe, and must not be… the caller wraps at
     exactly ONE layer: `EngineKnowledgeClient.executeSearchRpc`… Do not add a second wrap deeper

## 3. Checklist items

(C1-14) and §0.3's move (C1-10); neither needs a red window. §9 names the only reds allowed.

### C1-1 — the engine context type, and the fork check that precedes it

Design 3.4. One record in a contract module — `core` if the search port is to carry it (rule 6b
makes `core` the lowest module both halves see: `GpuSchedulingGauge.java:20-28` is the worked
precedent), `app-api` otherwise. Fields per 3.4 (`design.md:429-436`): client kind, client id,
session id, grant reference, source tier, and the **two independent axes** — `survival`
(`interactive` | `durable`) and `urgency` (`foreground` | `background`). The type must make
inference between the axes impossible: no `isForeground()` derived from survival, no constructor
that defaults one from the other outside the front's declared mapping
(`design.md:437-439`: "the default mapping … is a convenience at the front, not a rule in the
type"). The session id is attribution only and nothing durable may be keyed on it
(`design.md:441-445`).

**Before the record is written**, resolve the projection-versus-fork question against
`InvocationProvenance` (§0.7, **Q1**) and record the answer in the type's Javadoc with the
citation, so a reviewer does not have to re-derive it.

**Acceptance:** a test asserts the two axes are independently settable and that all four
combinations construct — including `durable` + `foreground` (the user-requested extraction of
3.4) and `interactive` + `background` (the idle self-benchmark), because a type that only ever
sees the two diagonal cases will grow an inference nobody notices; a test asserts no accessor
derives one axis from the other (reflection over the record's components plus a fixed expected
set, so a later convenience method fails it); the fork verdict is in the Javadoc with
`InvocationProvenance`'s file:line. *A test that constructs one context and asserts its getters is
not an acceptance — assert the independence, which is the property 3.4 spends a paragraph on.*

### C1-8 — admission per context at the front

### C1-9 — the aggregate cap, and why it is a different rejection

### C1-11 — urgency held by the work item, and the flip to background

Design 8 as amended by review seven (`design.md:1226-1234`). The increment is held by the **work
item**: an interactive call releases on return; a durable operation with `foreground` urgency holds
it until it completes **or until its waiting client is gone**, at which point urgency flips to
`background` and the flip is recorded on its row.

`ForegroundLoad`'s current shape is a strict `started()`/`finished()` pair in a `finally`
(`ForegroundLoadGate.java:126-136`, `ForegroundLoad.java:47-61`, with `finished()` clamped at zero
so an unbalanced decrement cannot make the gauge negative). A held increment that outlives the
request breaks the try/finally balance-safety the gate's doc calls load-bearing
(`ForegroundLoadGate.java:44-46`), so the holder needs an owner with a lifecycle — and the durable
operation's row is C2's (`design.md:1697`). **This is 17.8's fifth bullet firing.** C1 builds the
buildable half: the context carries the axis, the counter accepts a held increment with an explicit
release, and the flip is implemented for the one case C1 can observe (the HTTP connection closing).
The *recorded* flip on an operation row waits for C2, and the evidence record says unmeasurable,
not passed. See §10.

**Acceptance:** a test holds an increment across a simulated client disconnect and asserts the gauge
returns to its prior value (no leak) and that the flip happened; a test asserts a held increment
released twice does not decrement twice; the C2 dependency is named in the commit body and in §9,
not left for a reader to notice.

## 6. Section 16 rows stage C1 must leave exercisable

C1 produces no measurement (E does). Five rows are C1's to *make* exercisable, and it must not make
any other row unmeasurable.

- **aggregate bound** — C1's headline row (`design.md:1611`). After C1 both clauses are runnable:
  N contexts inside their limits hitting an executor cap, and the same offered load from one context
  rejecting the same number. The row's **second half** — the cursor-eviction clause — is **D2's**
  and stays unmeasurable until then; the evidence record says unmeasurable, not passed.
- **foreground search p95 and agent-loop API p95** (`:1601`) — the row cannot pass by shedding load,
  so it needs the admission rejection rate measured beside the p95 **and** rejections carrying the
  admission reason code, never a timeout. C1 is what makes "never a timeout" true; without it there
  is no code to carry.
- **memory** (`:1603`) — commit charge within the section 8 budget. C1 supplies the budget lines and
  `MaxDirectMemorySize`; the soak is E's. The bounded queues (C1-7) are what stop an unbounded
  `LinkedBlockingQueue` from being the growth the row would find.
- **semantic non-regression** (`:1614`) — the allowed-difference class *"reason codes that did not
  exist in split"* is one of exactly three the owner fixed (`design.md:1819`), and C1's two admission
  codes are the class's first real members. C1 must not add a fourth kind of difference; if the
  fixture starts differing on a field that is not a reason code, that is a regression.
- **request-time encoders** (`:1613`) — C1 must leave the session gate's one-batch-per-session bound
  reachable and must not let admission serialise the request-time encoder calls that run *inside* an
  admitted call (8: "Admission bounds how many requests enter, not the work each creates"). The row
  itself is D2's.

**Rows C1 must not break:** `recovery, process` and both hang rows (B's, and the request-file

## 7. The harness the checkpoint proof needs

The proof is *"a scripted agent loop hits admission and gets reason codes, never timeouts"*
(`design.md:1696`).

**Where it lives.** `scripts/jseval/lane-f/`, beside the lane's existing instruments
(`head-flag-run.sh`, `encoder-latency-probe.sh`, `fixture-cycle.sh`, `head-rss-sampler.ps1`,
`analyze-head-run.cjs`) — the directory PR 0 created for exactly this class of thing
(`design.md:115`). Node or shell, driving the live stack over HTTP; it is not a unit test, because
the property is about a real front under real concurrency.

**Shape.** `admission-loop.mjs`, three parts:

1. **The driver.** M concurrent clients, each issuing a search-and-chat loop against the live
   stack with a declared engine context, offered load ramped until rejections appear. It reads the
   admission cap from the running Engine (the component map is D2's, so at C1 it reads it from the
   config it started the stack with) rather than hard-coding it, so the harness cannot silently
   drift from the value under test.
2. **The oracle.** Every non-2xx is classified: an admission rejection (429 + the reason code +
   retry-after) is a **pass**; a timeout, a 500, a connection reset or a 503 that is not the upgrade
   barrier is a **fail**. The verdict is the count of the second class being zero — *not* "we saw
   some 429s", which is the vacuous reading.
3. **The aggregate arm.** The same total offered load from one context, asserting the same rejection
   count (§C1-9's second clause). Both arms in one run, because the row is the pair.

**How it is bounded.** A hard wall-clock cap of **five minutes** per arm, enforced inside the script
(`process.exit` on the deadline with a `TIMED_OUT` verdict, so an over-run is a legible failure
rather than a hung agent), a fixed request budget, and no retry loop around the whole run. It runs
under a declared `leaseDurationSec` on the shared dev stack (the lease model exists for exactly
this: minutes of busy-but-silent work). **It is never backgrounded past an hour** — tracked
background tasks are killed at ~60 minutes and `TaskStop` does not reap child loops
(`agent-lessons.md`); a campaign that needs longer is E's, not C1's.

**Wiring.** The harness needs the live stack, so it is not a CI gate; it is the checkpoint proof,
run once and recorded under `evidence/C1/` with its raw counts beside the verdict. Its **oracle**,
however, is unit-testable without a stack, and is: a self-test feeds it a recorded transcript
containing one timeout and asserts the verdict is `fail`. Ship the self-test in the same commit —
an oracle that has never seen a failing input is an oracle nobody knows works.

## 10. Stop rule (17.8)

Five triggers. Two fire.

**1. "Development resumes on `main` while the branch is open." — FIRES, already answered.**
Section 0 records the orchestrator's standing decision (2026-09-08): keep the single-branch shape,
`git merge origin/main` at every stage boundary, re-count, and revert to the incremental shape only
if a merge conflicts inside the blast radius. **C1's blast radius is wider than B's** — it touches
`modules/ui`'s request path, `app-api`'s two ports, `worker-services`' extraction and 56 executor
sites, i.e. most of the repo's Java. So the pre-stage count is not a formality here: run
`git diff --name-only <merge-base>..origin/main` filtered for `modules/ui/src/main`,
`modules/app-api`, `modules/app-services`, `modules/worker-services/.../extract`, `modules/ui-web/src`
and `Executors.new`, and if it is non-empty, merge before writing code, not after.

**2. "A stage needs a mechanism the table places later." — FIRES. Remedy applied, order unchanged.**
The urgency flip's recording needs C2's operation row (§9 row 2), and the retained-state caps for
cursors and readers need D2's cursor (§9 row 1). 17.8's remedy is "the item moves earlier with a
note in section 0; the checkpoint order itself does not change" — and here the item does not need to
move, because both unbuildable halves are *promises about state that does not exist yet* rather than
mechanisms C1 depends on. Recorded in §0 and §9. **No re-cut.**

**3. "Stage A's checklist outgrows the 917 consumer audit."** Stage-A-scoped; does not fire. But its
*principle* — time-to-complete is an architecture signal — is the one to watch on **C1-3**. If
threading a context through 33 methods and 39 files takes far longer than the mechanical estimate,
that is the code telling you the port is not one port, and the answer is to re-read 3.3 before
writing more of it, not to push through.

**4. "A gate row fails and its remedy is a process boundary."** Does not fire; E runs the rows.

**5. "A release must be cut mid-lane."** Does not fire as of this HEAD.

**Verdict: proceed, with four decisions on the orchestrator's desk before C1 starts** — Q1 (the fork
check), Q2 (the port-threading shape), Q3 (VDU's PDF load) and Q4 (`Mode.IN_PROCESS`). None is a
stop; all four are decisions 17.6 now routes to the implementation orchestrator (section 0, decision
authority, owner 2026-09-07), and all four are cheaper to make before the first commit than after
the third.

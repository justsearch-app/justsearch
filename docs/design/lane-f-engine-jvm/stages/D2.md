### D2-4 — the two-level session gate with aging, and the one-producer test

The [selected gate contract](../evidence/D1/d2-composition-and-request-design-2026-09-23.md#3-fairness-belongs-to-each-native-handle)
places FIFO foreground/background queues on each native handle and threads explicit admitted
urgency/deadline/cancellation through encoder acquisition. Producer tokens belong to each
encoder stage per EncoderSet, with one outstanding batch per token. Blue/Green tokens
remain distinct under the existing process resource envelope.

Design 4 (the request-time encoders paragraph as amended by review seven). Replace the unfair
semaphore in `NativeSessionHandle` (`:116`) with a gate: a foreground acquire (urgency from the
context, C1) goes ahead of any waiting background submit; background batch sizes are bounded by
the declared maxima; a background submit that has waited past the aging threshold (§2) is seated
next, once, and **every foreground call waiting at that moment is marked `passed`; aging is
suspended while any `passed` call is still waiting**; a foreground call is overtaken by at most
one aged batch in its whole wait. The gate's counters (seatings, passes, aged batches) are on the
component map. The **one-producer test** pins that exactly one thread produces background
batches per stage: a test starts a second producer and asserts the gate refuses it with a reason
(the gate takes a producer token issued once per stage), so a future second producer fails
loudly rather than breaking the one-batch bound silently.

**Acceptance (the unit clauses of 16's request-time-encoders row):** one background batch in
flight per session; foreground-first seating between aging periods; exactly one aged batch
seated per period under a saturating foreground load; with a foreground queue deeper than twice
the aging threshold, no foreground call is passed by more than one aged batch over its whole wait
and aging resumes once the passed calls are served — each as a deterministic test over a fake
session with controlled timing (no wall-clock sleeps); the producer-token test; the indexing
throughput test under a saturating foreground load shows background progress of one batch per
aging period plus one admission cap's drain (the compatibility clause). *A test that asserts
"foreground goes first" and nothing about aging is not the acceptance; the aging bound is the
whole item.*

### D2-5 — index-and-return at the port, with its durability test

Register955's memory projection/note un-designation consumer in engine-ports and

**Writer ticket and covering commit.** Add one process-local, non-reused writer epoch to the
existing `RuntimeSession` owner. The adapter returns a `WriterMutationTicket` containing only
that writer epoch and Lucene's actual mutation sequence number; the Worker retains the serving
generation, stable document identity and accepted source revision in its existing receipt.
`WritePathOps` currently discards the values
returned by `IndexWriter.updateDocument`, `softUpdateDocument` and `deleteDocuments`
(`modules/adapters-lucene/src/main/java/io/justsearch/adapters/lucene/runtime/WritePathOps.java:75-105,113-138,154-195`).
Return the sequence through `IndexingCoordinator` without bypassing
its `dispatchLock`; the coordinator is the sole mutation entry and deliberately serializes RMW,
ingest and delete (`.../IndexingCoordinator.java:21-49,345-370,458-474`). The ticket becomes
invalid when the runtime/writer epoch changes; equal bare sequence numbers from different epochs
never cover one another.

Extend the existing `RuntimeSession.writeBarrier`, rather than add a second commit coordinator.
Mutations already take its read side outside `dispatchLock` (`RuntimeSession.java:232-246`;
`IndexingCoordinator.java:62-94`), so retain the lock order **generation/lifetime route ->
write-barrier read side -> `dispatchLock`**. A covering commit takes the barrier's write side,
captures the completed sequence before that exclusive interval, calls Lucene commit, and
publishes the successful commit's returned sequence for that writer epoch. A no-op commit
returning -1 uses the captured pre-commit maximum; neither case samples a later maximum.
`CommitOps.commit()` currently returns elapsed time and synchronizes only its own metadata plus
Lucene call
(`modules/adapters-lucene/src/main/java/io/justsearch/adapters/lucene/runtime/CommitOps.java:77-120`);
it must return successful commit coverage beside elapsed time. It must
not sample a later maximum after releasing the barrier. Commit failure or ambiguous writer loss
publishes no watermark and fails every waiter that depended on that attempt.

Every commit route—timer, explicit idle/settle, cutover and shutdown—must enter this same
barrier-aware `CommitOps` primitive, so no successful Lucene commit can bypass watermark
publication. Likewise, every mutating `WritePathOps` route, including batch, RMW, maintenance and
broad delete, remains under the coordinator's existing barrier and `dispatchLock` order. The
accepted projection methods need to return their own actual sequence ticket. Commit captures
`IndexWriter.getMaxCompletedSequenceNumber()` under the exclusive write barrier immediately
before committing: this existing writer authority includes every completed mutation, including
a successful first call before a later call in the same wrapper failed. Do not maintain a second
session mutation counter or synthesize a sequence for physical force-merge maintenance. A focused
whole-package audit must reject any raw `IndexWriter` mutation outside these two owners. Do not
move commit under `dispatchLock`: the write side of `writeBarrier` already drains mutation calls,
and reversing that order would create an avoidable lock cycle.

**2026-09-30 whole-package audit correction.** Sol found all logical document writes confined
to package-private `WritePathOps` behind `IndexingCoordinator`. Preserve actual return values
for `indexSingle` and parent-plus-chunks delete (the highest successful second delete); existing

cancelling it detaches that waiter, while the existing registered executor retains the wave.

The audit also found default commit-on-close bypasses the operational commit funnel. Set runtime
writer configuration to `commitOnClose(false)` and require close to perform the common explicit
covering commit whenever the exact writer sequence exceeds successful coverage. `pendingDocs`
remains a cadence heuristic, never a close/coverage authority; broad deletes and RMW do not
consistently increment it. Empty-index bootstrap and corruption-recovery commits occur outside
the live session epoch and retain their explicit lifecycle exceptions. Extend the existing
commit-funnel architecture test with mutation ownership and retire its implicit runtime-close
commit allowance. Required proof includes parent/chunks partial failure, broad/RMW/delete-all
coverage, force-merge plus explicit commit, and close without an implicit commit. This is the
smaller design because it uses Lucene's exact sequence authority rather than projecting another
counter across every legacy mutation wrapper. Root then refuted an overlooked Lucene detail
with the exact installed10.4 library at `tmp/lane-f-d2-writer-sequence-probe-r1.log`: mutation1,
pre-commit1, successful commit return3, post-commit3, repeated no-op -1. Commit itself advances
the sequence. Publishing only1 would leave close permanently seeing uncovered3. The successful
commit return is therefore coverage; only -1 falls back to the captured pre-commit maximum.
Independent Sol agrees. Preserve that original red probe and add deterministic regressions for
both outcomes. No implementation or passing runtime test is implied by this audit.

Waiter registration and committed-watermark inspection share one short monitor so completion
cannot be lost between mutation and registration. The existing registered `CommitOps.commitTimer`
executor owns each pending group-commit wave, with a fixed deadline 250 ms after its first
registration. Later same-epoch waiters join without extending that deadline. Caller cancellation
removes only its waiter; even cancellation of every waiter cannot discard the admitted target.
At most one wave is in flight; arrivals during its commit form the next pending wave. Registration,
wave claim and successful coverage publication use the short monitor, which is never held while
acquiring the barrier, invoking Lucene, notifying callbacks or waiting for client work. After
acquiring the write barrier, a wave rechecks coverage and skips Lucene if another commit already
covered its target. Failure publishes no watermark and fails the dependent cohort; scheduling
rejection rolls back admission rather than stranding it. No new executor or durable log is added.

The first ignored-draft review found three concrete close races. Seal terminal writer admission
under the same short monitor before releasing the drain barrier; a late ticket cannot schedule
work against a disposed tragic writer. Track actual common-commit owners through future completion
and telemetry/listener callbacks, including direct commits outside the scheduled wave. Close waits
for that count as well as waves before atomically sealing teardown. Reusing generation task owners
alone is insufficient: direct commit callers do not uniformly hold them, and close-owned commits
must remain admissible after normal generation admission closes. Moving all direct calls onto the
executor would change their existing synchronous and lock-order contracts. The transient count
inside CommitOps is the smaller ownership extension. On any close deadline exhaustion, detach and
fail every unresolved waiter outside locks while retaining admitted wave targets and resources for
retry. None of these observations earns coverage; only actual successful Lucene commit does.
The eight private draft classes compile against the installed libraries at
`tmp/lane-f-d2-draft-compile-r5.log`; they remain unapplied and unverified
in production. Thirteen private real-Lucene tests pass at
`tmp/lane-f-d2-private-coverage-r4.log` with source/library-hash/command/classpath/revision
evidence beside it. Root corrected two callback races in the draft: remove a
failed in-flight claim before exceptional completion can synchronously register
another waiter, and seal uncovered admission under WRITE before terminal-writer
failure callbacks run. Independent Sol then refuted a monotonicity defect:
already-covered tickets must still return success after later writer tragedy.
Inspect the successful watermark before terminal rejection under the same short
monitor; failure seals only uncovered admissions. The thirteen-case run proves that
correction, actual MMapDirectory.sync stalling with resource retention and safe retry,
and the first-wave scheduled delay within250ms without resetting its task identity.
The delay assertion does not claim fsync completion within250ms. An isolated mutant
that rejects the earlier certificate after later tragedy fails that exact regression
at `tmp/lane-f-d2-monotonicity-mutant-red.log`; the accepted source is untouched.
Independent Sol accepts the private core and port design. Production application,
accepted-operation propagation, production tests and installed immediate forced-kill
proof remain required; the draft does not yet satisfy D2-5 acceptance.

**2026-09-30 cancellation and close refutation.** Independent Sol rejected caller-owned execution:
leader cancellation could strand the group. The existing registered scheduled executor is the
simpler owner, but its current shutdown policy discards delayed work. Separate cancellation of
periodic safety-net scheduling from shutdown of that executor. Close freezes a target after
draining admitted mutation readers. It rejects targets beyond that fence, while pre-close tickets
at or below it may attach afterward and already-covered tickets complete immediately. It
allows admitted waves and their retained task owners to finish against the still-live writer,
waits for pending/in-flight work, and only then shuts down the executor and writer. Timeout must
fail unresolved waiters and retain resources still used by an executing wave; it cannot report
durable success or destroy the writer underneath the wave. Do not add a blanket closing-state
rejection to the common commit primitive: already-admitted work remains authorized until teardown.

Sol also proved an existing lock-order obstacle: `RunningRuntime.drainAndClose` holds the write
barrier while `RuntimeSession.close` waits for task owners and the scheduled executor. A scheduled
wave blocked on that barrier would deadlock close. The required two-phase drain performs the
write barrier solely to drain prior readers and capture the close target, then releases it before
submitting the common DRAIN wave to the existing executor. That wave owns its own barrier and
propagates failure. One absolute deadline covers the drain, commit future, generation owners and
executor exit; direct session close retains its existing five-second default. Stalled fsync remains
executor-owned so the closing caller can return bounded without destroying the writer. Successful
coverage and callback completion follow barrier release. Only after coverage and actual wave/owner
exit may session close dispose resources. Nonterminal failure or timeout retains them for retry;
known tragic/already-closed writers instead fail all waiters and retain the existing disposal path
without a clean marker. The old outer
reentrant barrier around commit would still hold the lock through callbacks and is superseded.
Keep `draining=true` throughout. Several
current mutation routes bypass `guardBackpressure`, so this requires a central post-acquisition
draining/closing check in `IndexingCoordinator.acquireReadLockTimed`: unlock and throw the existing
DRAINING failure before any mutation. Every previously admitted reader is drained by the write
lock; every later reader is rejected. This preserves dispatch serialization and closes the
unlock-to-close interval without another state machine. Evidence owners are
`RunningRuntime.java:217-255`, `RuntimeSession.java:741-755,796-844`,
`IndexingCoordinator.java:62-95,121-248,507-515` and
`DefaultEngineExecutorRegistry.java:326-329`. These are design requirements, not implemented proof.

`NRT` waits for the ticket's exact reader visibility (`maybeRefreshBlocking` is currently called
at `WorkerIngestService.java:305-314`). `DURABLE` first waits for a successful covering watermark
for the same writer epoch and sequence, then establishes reader visibility before returning an
upsert receipt. An already-absent delete still submits the identity delete and requires its ticket
to be covered; absence observed from a reader or cache is not durable proof. During a rebuild,
the existing D1 route admits the projection to the candidate journal before mutating the serving
writer (`WorkerIngestService.java:291-310`); durable success therefore requires both that replay
obligation and the serving-writer covering commit. Activation must drain/transfer that mutation
route and cannot strand an accepted ticket.

**Semantic visibility comes from the exact D1 view.** A BUILDING generation is insufficient:
BESIDE retains native A, while IN_PLACE publishes a lexical view. D1 selects IN_PLACE and calls
`beginInPlaceCandidateBuild`
(`modules/indexer-worker/src/main/java/io/justsearch/indexerworker/server/KnowledgeServer.java:3444-3457`);
that method publishes `TextOnlyCandidateView` under the
existing publication locks (`KnowledgeServer.java:3506-3564`). The wrapper deliberately reuses
the incumbent `WorkerIngestService`
(`modules/worker-services/src/main/java/io/justsearch/indexerworker/server/DefaultWorkerAppServices.java:1338-1347`),
so the service cannot infer
visibility from its own identity or from `buildingGenerationForFileAdmission`.

Add a small internal semantic-visibility value to `WorkerAppServices`: ordinary
`DefaultWorkerAppServices` reports semantic-now and `TextOnlyCandidateView` reports
semantic-at-activation. `EngineKnowledgeClient` already captures the exact serving lease/view for
each call
(`modules/app-engine/src/main/java/io/justsearch/app/engine/EngineKnowledgeClient.java:656-668`)
and resolves the ingest service inside that captured view (`:891-900`); pass the value
through `WorkerIngestCalls` with the projection. The Worker combines that D1 fact with the proven
NRT/durable level when constructing the receipt. This preserves already-issued view semantics and
distinguishes simultaneous BUILDING+BESIDE from BUILDING+IN_PLACE without a new public API.

**2026-09-30 receipt representation decision.** The existing three-value visibility
enum cannot represent a durable text-only result without losing one of the two
proved facts. Extend that owning enum with
`DURABLE_TEXT_ONLY_SEMANTIC_AT_ACTIVATION`; the existing
`TEXT_ONLY_SEMANTIC_AT_ACTIVATION` continues to denote NRT text-only visibility.
This is the fourth combination of the existing durability and serving-view
facts, not another state authority. Adding a separate receipt record or carrying
an unbound global encoder flag would duplicate the source of truth or relabel
issued calls. The captured WorkerAppServices view supplies the semantic fact;
the actual covering commit supplies durable success.

The rejected alternative is a supplier/setter exposing
`KnowledgeServer.recordedCandidateInPlace` directly to `WorkerIngestService`. Although the flag
already exists (`KnowledgeServer.java:651-659`), it is global rather than bound to the issued
serving lease; because native and lexical views share the same ingest service, a transition could
relabel an already-issued request. Inferring from encoder `RELOADING` is also invalid: encoder
recovery and generation composition have different owners, and BUILDING alone cannot reveal the
physical BESIDE/IN_PLACE decision.

**Required proof.** Add deterministic adapter tests for a commit covering a ticket and one that
does not, equal sequence numbers in two writer epochs, waiter registration racing commit
completion, N callers coalescing to one commit, commit failure, cancellation after the effect,
and teardown with outstanding waiters. Add port/Worker tests for canonical accepted-key
propagation, keyless `DURABLE` refusal, upsert and already-absent delete, plus held D1 views showing
BUILDING+BESIDE returns ordinary NRT/durable visibility while BUILDING+IN_PLACE returns
text-only/semantic-at-activation. Extend the switch-buffer test through activation so an
acknowledged update/delete is replayed and a delete cannot resurrect. Finally run the installed
forced-kill fixture with controlled commit timing: durable update and authoritative deletion
survive restart, while the adverse NRT case is visible before kill and absent after restart. These
are required future checks, not evidence recorded by this consolidation.

**Acceptance (16's durability row):** a `durable` write is searchable after an immediate forced
kill and restart (the installed-process tier, B17's fixture shape); an `nrt` write is searchable
before the next commit and **may** be absent after the kill (asserted as the adverse case, so the
two durabilities are shown different); the coalescing test asserts N concurrent `durable` calls
inside one deadline produce one commit; `SwitchBufferDurabilityTest`'s rule applies: a failed
commit makes `durable` return failure, never `durable` success.

### D2-6 — the cursor generation token, reader pinning, and `cursor expired`

The [selected cursor lifetime contract](../evidence/D1/generation-native-cursor-design-2026-09-23.md#6-cursors-retain-a-generation-binding-not-just-a-lucene-reader)
binds every page to its exact reader/runtime/encoder view. Eviction prevents new pages
but releases permits only after actual active-page exit and reader release; if capacity
cannot yet be reclaimed, refuse/delay a new cursor. Side-by-side activation retains old
resources to expiry; in-place retirement first expires affected cursors and drains pages.

Design 4 ("Streaming through contracts"), 7.4 (cursors), 8 (retained state). A search page
cursor carries the generation id and a searcher token; the core pins a reader per live cursor
through a per-generation `SearcherLifetimeManager` (Lucene's primitive) in `RuntimeSession`,
released on cursor expiry (§2) or eviction; the caps come from `governance/retained-state.v1.json`
(cursors per context and aggregate, pinned readers; C1-12's `awaitingProducer: D2` rows get
their producers here, and the coverage test's kinds become live). Eviction is oldest-first per
context; an evicted or generation-retired cursor answers the **new** code `CURSOR_EXPIRED`
(distinct from `CURSOR_INVALID`, which stays for a malformed cursor; the message at
`errors.en.properties:43` is corrected to say "invalid"). D1-7's activation retires the old
generation's pinned readers per 7.4: served to normal expiry if the old encoder is still loaded,
`CURSOR_EXPIRED` if it is not, never silently served from the new generation. `searchAfter`
keeps its stateless decode (`ReadPathOps.java:421-426`) but resolves against the pinned searcher
when the cursor carries a token.

**Acceptance (16's aggregate-bound cursor clause and the generation row's cursor clause):** a
client paging one request at a time against a changing index sees its oldest cursor evicted with
`CURSOR_EXPIRED` once the per-context cap is reached; the pinned-reader count on the component
map never exceeds its cap; a cursor opened before activation pages to expiry (encoder loaded) or
fails `CURSOR_EXPIRED` (encoder unloaded) and never returns new-generation evidence — asserted
by a document that exists only in the new generation; memory holds through the run (E). The
readiness code parity tests green with the new code; `run-ui-web-gates` green with the FE
handling (a page that expires re-searches, no error toast).

# Lane F stage C2 — operations: implementation checklist

Written from the three inputs 17.6 requires: the stage's row in `design.md` 17.3,
`verified-facts.md`, and a fresh read of the code. Drafted 2026-09-08 at `e692b86ef` and
**re-grounded 2026-09-09 at `be47faa40`, the stage B completion head**, by a code-verified pass:
every `file:line` below was re-resolved by content at that commit; a claim that did not survive is
corrected in §0 (the dated block "Re-grounding, 2026-09-09") rather than silently rewritten.
`design.md` is cited by **section** (it was consolidated after the draft); code is cited by
`file:line` at `be47faa40`; `verified-facts.md` is cited by bullet subject, not line.

The six questions the draft raised are **decided** in `design.md` section 0 (2026-09-08), and one
of them — where the operations table lives — was **re-decided on 2026-09-09** on a fact the draft
did not have (§0 re-grounding item R1): the table goes into its own store, `operations.db`, and
no durable store's identity changes in lane F. §11 lists the decisions in one line each; the
items are written to them.

Stage C2 in one line (17.3 row C2, as amended 2026-09-09): **the operations table in its own
registered store; acceptance, effect and completion in a fixed order stamped by the table's own
key; the client-supplied key with the inert `idempotencyKey` field getting its first consumer;
the outcome query as the durable swap of `OperationHistoryStore`, answering all five states with
`expired`, `history since` and `version conflict` on the global accepted-settings revision; and
resume under the four conditions for ingestion and reindex bundles, with ingestion's per-file
recovery re-based on it.**

### C2-5 — retention, the row cap, `expired` and `history since`

Design 7.6 (`design.md §7.6`, as amended 2026-09-10), 17.7's C2 row; the full mechanism is the
design record §2. *(rewritten 2026-09-10)*

- **The boundary.** A missing key answers `expired` if its UUIDv7 embedded time is earlier than
  `history since`, else `unknown`. Five minutes bounds accepted future skew on ingress;
  it is not added again on lookup. A present row always wins, whatever the key time.
- **`history since`.** One value in `operations_meta`, zero for a genuinely new store, **monotonic**,
  advanced transactionally with eviction to max(existing fence, newest evicted UUIDv7
  timestamp +1ms). Corruption quarantine sets it to now + admitted future skew +1ms.
  A fence ahead of now temporarily refuses missing current-time keys with the remaining
  retry delay; do not tell a client to mint another current-time key. Never the oldest
  survivor (§2 explains the gap that rule hides).
- **Retention.** Terminal rows whose `completed_at` is older than 30 days are pruned; the cap
  (100 000) evicts the oldest terminal rows first; non-terminal rows are never pruned by age. Both
  run from one registered Head background timer (`head.operations-retention`, hourly, and once at
  open), the shape of `KnowledgeServer`'s periodic cleanup (`:2083-2126`), not a fork of
  `cleanupOldJobs`, which prunes a different store under a different lock.
- **Restore.** Quarantine and creation are the only restore transitions the Engine performs; an
  external file rollback is outside the contract and the register row says so.

**Acceptance:** a test asserts an aged-out key answers `expired` **and not `unknown`** — the two
are one line apart in the implementation and one word apart in a bad test; a test asserts both
sides of the boundary around the key-time `history since` fence; a test asserts `history since` is monotonic
under retention, under cap eviction and under quarantine, **and** that a long-running row older
than the evicted rows still leaves every evicted key answering `expired` (the oldest-survivor
counterexample); a test asserts a v4 key and a far-future v7 key are refused before acceptance; a
test asserts a cap reached with only non-terminal rows refuses acceptance and evicts nothing.
Also prove a fresh store accepts current-time keys, ordinary eviction does not add five
minutes to the boundary, evicting an admitted future key expires it, and an injected
clock crossing a quarantine/future-key fence restores acceptance without a retry duplicate.

## 7. The forced-kill procedure the checkpoint proof needs

**Where it lives (R7).** The installed-process tier stage B built: `modules/system-tests`'s
`integrationTest` task (`build.gradle.kts:171`, depends on `:modules:ui:installDist` `:178`, the
scenario scripts declared as inputs `:179-182`), driving `scripts/supervisor-conformance/*.mjs`
scenarios against the dev-runner's real child binding with the harness-only cooldown. C2 adds
`operation-resume-scenario.mjs` and a JUnit entry `OperationResumeE2ETest` in the shape of
`EngineSupervisedRecoveryE2ETest` (`@Timeout`, `@ValueSource` of scenario names, Windows
`assumeTrue` on the identity collector, owned-run cleanup `:132-185`). Nothing new is written
under `scripts/jseval/lane-f/`, which still contains no forced kill.

**The three kill points** (design 16), driven by a **test-only fault switch** carried on the
operation's context rather than by timing, because a timing race cannot assert *which* point it
hit. The switch is a harness-only environment key read by the composition root, refused unless
`JUSTSEARCH_SUPERVISOR_HARNESS=1` is also set (the gate B8 established for its overrides):

1. **before the acceptance row** — after restart, the key answers `unknown` and the stores show
   no effect;
2. **after acceptance, before the first effect** — `accepted`, no effect;
3. **after an effect, before its checkpoint** — `running` or `failed` with a unit count the
   scenario cross-checks against the `jobs` rows and the Lucene doc count.

At each point, after the restart: query by the client key, then **retry under the same key** and
assert no duplicate effect (doc count and `jobs` row set unchanged). The same three points run for
a **write** (an ingest of a small root) and for a **reconfigure** (`POST /api/settings/v2`) — six
scenarios.

**The kill itself.** `process.kill(pid, 'SIGKILL')` against the Engine PID from the runtime
manifest after `process-identity.cjs` confirms PID, creation time and command line (B17's
`processing-replay-scenario.mjs:10-38` is the code to copy) — never a name sweep, never an
`agent-spawn` helper. The dev-runner supervisor restarts it; the scenario **asserts** the restart
from `supervisor.v1.json` (`state === 'restarting'`, `restartCount === 1`,
`lastExit.counted === true`) rather than racing it, and reads the SQLite rows **after death and
before the successor starts** (the harness cooldown exists for exactly this window).

**Bounding.** Each scenario is one owned run: start (about 40 s cold), ingest a fixed small
corpus, kill, restart, query — budget 90 s per scenario inside the class's `@Timeout`, about ten
minutes for all six; B17's five scenarios ran in 1m56s. Never a background task over an hour; a
scenario that cannot finish in its budget is cut wrong, not run longer.

**What it asserts.** For all six: the kill point was reached (from the fault switch's own log
line), the post-restart answer equals the expected state, the unit count matches the stores, the
same-key retry moved nothing, and `portsClosed: true` at cleanup. A scenario the driver could not
reach is a **failure**, not a skip — the predictable evasion is "kill point 2 was hard to hit, so
five of six passed".

**Before the table exists (batch 1)**, the scenario file and the JUnit entry land with the
**write** scenarios only asserting what is true today — PROCESSING replay after a kill mid-batch
(B17 proves it) and no duplicate document after retry — so the harness runs green on day one; the
stamps and the key turn the three points on per item. A placeholder that reds is a defect; a
scenario that passes vacuously is the other defect, so each point's assertion is added with its
item, never pre-written as `assumeTrue(false)`.

### 2026-09-09 C1 integration dependency: scheduled outcomes

Static grounding at `b0078e603` plus C1 batch-3 changes found that BackgroundRunService
logs an execution-time admission refusal and returns null; its timer ignores that result.
InteractionThreadController has already answered scheduled=true, while AgentLoopService only
creates its model-run row after admission. C2 must persist scheduled acceptance through the
same operations.db/history authority before timer acceptance, propagate the client operation
key, and write a typed terminal outcome for admission or executor refusal against that row.

C1's bounded scheduler must synchronously report submission rejection; C1 does not claim
persistent scheduled outcomes. This is required C2 acceptance, with a regression exercising
refusal before an AgentRunStore row exists and outcome lookup after restart. No owner decision
or out-of-lane deferral is required.

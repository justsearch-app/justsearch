### C2-8 — resume under the four conditions: ingestion

Design 7.5 (`design.md:986-994`, `:1032-1035`). Ingestion of a root is an **ongoing operation

## 7. The forced-kill procedure the checkpoint proof needs

**Where it lives.** `scripts/jseval/lane-f/kill-resume-run.sh`, beside the existing
`head-flag-run.sh` (156 lines) with `analyze-kill-resume.cjs` beside `analyze-head-run.cjs` —
the split PR 0 established (`design.md:114-116`). Bash under Git Bash, the same shape as
`head-flag-run.sh`: `set -u`, positional `<label> <outdir> [api-port]`, `phases.json` written by
`phase_mark` (`:31-35`), readiness by a bounded `/api/health` poll (`:37-53`), start and stop
through `node scripts/dev/dev-runner.cjs` (`:74-85`, with `--lease-duration-sec`). Nothing in
that directory does a forced kill today (grep for `taskkill|Stop-Process|SIGKILL` over all five
files returns only the graceful `stop --active` helpers) — the warm restart at `:147-152` is a
graceful stop-then-start. The PID handle the driver needs is already extracted from
`/api/runtime/manifest` at `:101-103`.

**The three kill points** (`design.md:1605`), driven by a test-only fault switch rather than by
timing, because a timing race cannot assert *which* point it hit:

1. **before the acceptance row** — expect `unknown`, and the stores show no effect;
2. **after acceptance, before the first effect** — expect `accepted`, and the stores show no
   effect;
3. **after an effect, before its checkpoint** — expect `running` or `failed` with a unit count
   the analyzer cross-checks against the `jobs` rows and the Lucene doc count.

At each point, after the restart: query by the client key, then **retry under the same key** and
assert no duplicate effect (doc count and `jobs` row set unchanged). The same three points run
for a **write** (an ingest of a small root) and for a **reconfigure**
(`POST /api/settings/v2`).

**The kill itself.** `taskkill /F /PID <pid>` against the Engine PID from the runtime manifest —
never a name sweep, and never an `agent-spawn` helper (`branch-safety.md`: a registered spawn is
named, never hand-killed). Stage B's supervisor will restart it, so the driver runs with the
dev-runner supervisor active and **asserts** the restart happened rather than racing it.

**Bounding.** Six scenarios (3 points x 2 subjects), each start (~40 s cold, ~15 s warm) ->
ingest a fixed small corpus -> kill -> restart -> query. Budget **90 s per scenario, 12 minutes
wall clock for the whole driver**, enforced two ways: a per-scenario `timeout` inside the script,
and bounded polling in the `head-flag-run.sh:39` shape rather than an unbounded wait. **Never a
background task over an hour** (`agent-lessons.md`: tracked background tasks are killed at ~60
minutes and `TaskStop` does not kill child bash loops) — a driver that cannot finish in twelve
minutes is cut wrong, not run longer.

**What it asserts.** `analyze-kill-resume.cjs` exits non-zero unless, for all six scenarios: the
kill point was reached (asserted from the fault switch's own log line, not inferred), the
post-restart answer equals the expected state, the unit count matches the stores, and the
same-key retry moved nothing. A scenario the driver could not reach is a **failure**, not a
skip — that is the predictable evasion here ("kill point 2 was hard to hit, so five of six
passed").

## 10. Stop rule (17.8)

Five triggers. Two fire.

**1. "Development resumes on `main` while the branch is open." — FIRES, already answered; re-run
the count.** Section 0's dated entry of 2026-09-08 records the decision: keep the single-branch
shape, `git merge origin/main` at every stage boundary, re-count, and revert to the incremental
shape only if a merge conflicts inside the blast radius. C2's blast radius is narrower than B's
and mostly ours (`SqliteSchema`, `SqliteJobQueue`, `governance/store-*`, `WorkerIngestService`,
`OperationHistoryStore`) — but `updater.rs`, `scripts/release/` and `contracts/wire/` are **not**,
and a release-tooling change on `main` conflicts directly with C2-1. Re-run
`git diff --name-only <merge-base>..origin/main` filtered on those paths at stage start.

**2. "A stage needs a mechanism the table places later." — FIRES twice; this is the item to put
to the orchestrator before C2 starts.**

- **`version conflict` needs the applied configuration revision, which 17.3 places in D1**
  (§0.9). Unlike stage B's case there is no buildable half that leaves the row correct: a
  refusal that compares nothing is not a refusal. 17.8's remedy is "the item moves earlier with
  a note in section 0; the checkpoint order itself does not change" — **Q4** puts the two shapes
  with a recommendation.
- **The reindex's convergence contract needs the journal and replay, which are D1's**
  (`verified-facts.md:156-160`). Here there *is* a buildable half — the row, the plan, the
  resume, the two lists — and the unbuildable half is an activation decision 16 cannot measure
  until D1 anyway, so this resolves the way B's step 3 did: no re-cut, recorded in §9 row 1.

**Trigger 4 ("a gate row fails and its remedy is a process boundary") does not fire, but note
the shape it would take.** No gate row has been run (E runs them). If the **dead-Engine upgrade**
row fails because §0.5's compatibility rules make an operations table un-upgradeable in place,
the remedy under the section 2 rule is a *store* boundary, not a process boundary — so it does
not reopen 2 and 14. Say that explicitly if the row fails, because the two look alike from the
gate's side.

**Triggers 3 and 5 do not fire.** Trigger 3 is stage-A-scoped. No release is being cut — but
C2-1 touches release tooling, so a mid-lane release is more expensive for C2 than for any earlier
stage.

**Verdict: proceed, with Q2 and Q4 decided at brief time.** Neither is a stop; both are changes
the orchestrator decides and records dated in section 0 (owner delegation, 2026-09-07).

# jseval dependency lock — tempdoc 792 §6.
#
# WHAT THIS FILE IS
# jseval (scripts/jseval/pyproject.toml) declares floor-only constraints with no upper
# bounds and no lockfile, so `pip install -e scripts/jseval` can resolve a DIFFERENT
# dependency graph on every run as new releases land upstream. jseval produces the
# numbers behind this project's PUBLIC published claims (the agent-utility replay gate
# in .github/workflows/ci.yml's `public-claims` job runs it in CI), so an unpinned
# resolver is a reproducibility hole in the measurement harness itself. This file pins
# the exact transitive closure of the BASE install only — i.e. exactly what
# `pip install -e scripts/jseval` resolves with no optional extras — because that is
# exactly what CI installs (ci.yml:53) and is therefore the only surface CI can validate
# against. The `[project.optional-dependencies]` extras (ranx, ui, config, ner, scan,
# agent, dev) are intentionally NOT locked here: CI never installs them, so there would
# be no CI signal to catch a stale extras-pin, and the `agent` extra alone pulls a ~80
# package closure through inspect-ai that deserves its own scoped lock if it is ever
# installed in CI. Rejected alternative: lock every extra too — rejected for the reason
# above (unverifiable pins are worse than no pins; `check-jseval-lock.mjs` would have
# nothing to hold them against).
#
# HOW TO USE
# This is a pip CONSTRAINTS file, not a requirements file — it does not install
# anything by itself. Wire it with `-c`:
#
#   pip install -e scripts/jseval -c scripts/jseval/requirements.lock.txt
#
# `-c` only pins the version of a package that pip already decided to install (because
# pyproject.toml's own dependency list pulled it in); it never forces the install of a
# package pyproject.toml doesn't already require. That is what lets ONE file serve both
# the Linux CI platform and Windows/macOS dev machines: `colorama` below carries the
# same `platform_system == "Windows"` marker click/tqdm declare on it, so the pin is
# live on Windows and a harmless no-op on Linux/macOS where colorama is never installed.
#
# CROSS-PLATFORM HONESTY
# No hashes. `pip hash`-verified pins are wheel-file-specific, and this repo's single CI
# platform (ubuntu-latest / manylinux) differs from common local dev platforms (this was
# generated from a Windows dev machine, see below) — a hash-pinned lock generated against
# one platform's wheels fails hash verification against another platform's wheels for the
# identical version. Plain version pins (no hashes) give version-reproducibility across
# machines and time without that cross-platform failure mode; this is the documented
# honest trade-off, not an oversight.
#
# REGENERATION
# Generated 2026-07-29 against CPython 3.13 (matching ci.yml's
# `actions/setup-python@v7` pin: `python-version: "3.13"`) targeting the
# manylinux2014_x86_64 platform tag (matching ci.yml's `public-claims` job:
# `runs-on: ubuntu-latest`), using pip's cross-platform dry-run resolver (no network
# install, no target-platform interpreter required to run this command):
#
#   python -m pip install --dry-run --ignore-installed --report report.json \
#     --python-version 3.13 --implementation cp --abi cp313 \
#     --platform manylinux2014_x86_64 --only-binary=:all: \
#     -e scripts/jseval
#
# Known limitation of that command (verified empirically while generating this file):
# pip's --platform/--implementation/--abi flags retarget which WHEEL TAGS it will
# accept, and correctly retarget `python_version`-family markers, but do NOT retarget
# `platform_system`/`os_name`/`sys_platform` markers — those still evaluate against the
# HOST machine running pip, not the requested target. Concretely: running the command
# above from Windows reports `colorama` as part of the install set (because
# `platform_system == "Windows"` evaluates true on the *generating* Windows host), even
# though it correctly would NOT install on the real Linux CI target. This file corrects
# for that by hand-verifying colorama's marker from click/tqdm's own metadata
# (`requires_dist`) and keeping the marker in the pin below rather than trusting the
# dry-run's flattened "would install" list — the marker is then evaluated for real by
# whichever machine actually runs `pip install -c` (correctly, since marker evaluation
# at real install time is not subject to the dry-run/cross-target limitation above).
#
# After regenerating, extract the pinned versions from report.json's `install[].metadata`
# (name + version), drop `jseval` itself (this file constrains its dependencies, not the
# editable package), and re-add the `colorama` platform marker by hand as this file does.
# `node scripts/ci/check-jseval-lock.mjs` fails the build if pyproject.toml's floors and
# this file disagree (a dep added, or a floor raised, without regenerating) — its failure
# message repeats this regeneration recipe.
#
# Delta note: 3.13 is genuinely absent from this dev machine's default toolchain but was
# available via the already-in-use scoop `versions` bucket (`scoop install
# versions/python313`), so this was generated against the real CI interpreter, not an
# approximation. If a future regeneration must fall back to a different local
# interpreter, note the version delta in this header rather than silently overwriting it.
